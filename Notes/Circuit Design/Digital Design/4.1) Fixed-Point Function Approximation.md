**Specification.** Input $X$ in a fixed-point format $\mathrm{ufix}(-1,\ell_X)$ (domain $[0,1)$) or $\mathrm{sfix}(0,\ell_X)$ (domain $[-1,1)$); output $\widetilde f(X)$ in $\mathrm{sfix}(m_{\text{out}},\ell_{\text{out}})$; accuracy either **faithful** ($<1$ ulp, the usual target) or **correctly rounded** ($\le\tfrac12$ ulp); minimize **area** first, latency second. Formats and ulp are as defined in [[1.1) Number Formats]] and [[1.2) Error Accuracy]].

Stated as an optimization problem: *given $f$, an input format, an output format and an accuracy target, build the cheapest circuit whose output is within that target for every input.* Everything in Part 4 — [[4.2) Table-Based Function Evaluation]], [[4.3) Polynomial Approximation]], [[4.4) Digit Recurrence for Algebraic Functions]] — is a different answer to that one question. This note fixes the question.

The phrase **"for every input"** is doing real work. A fixed-point input format has finitely many values — $2^{n}$ of them for an $n$-bit input — so "for every input" is a finite statement, and an accuracy claim about the circuit is in principle decidable by exhaustive enumeration. The book leans on exactly this: correct rounding of elementary functions is treated only for precisions up to 24 bits, *"where the construction of the architecture can rely on an exhaustive enumeration of all correctly rounded values using multiple-precision software"* (p. 488). Software floating-point never gets this luxury: a `double` library faces $2^{64}$ inputs and must fall back on proof. Hardware arithmetic at $\le 24$ bits can simply check.

## Defining domain and range

It seems natural for a generator to take the interval $[a,b]$ as a parameter, and early generators did. It is the wrong interface. Because **$f$ itself is an input to the generator**, any change of variable can be folded into the function specification instead, so the generator never needs to know $a$ and $b$ — interval bounds "only add redundancy and complexity to the code of the generator" (p. 480).

The two standard domains are therefore

$$[0,1) \;\longleftrightarrow\; \mathrm{ufix}(-1,\ell), \qquad [-1,1) \;\longleftrightarrow\; \mathrm{sfix}(0,\ell)$$

and the interval parameter collapses to one Boolean, `signedIn`. Both intervals are **open at 1** because the largest value of a fixed-point format is $1-2^{\ell}$, not $1$. That asymmetry is not cosmetic; it is the source of every trap in the next section.

Worked change of variable, for the sine (Fig. 16.3–16.4, pp. 480–481):

| Target | Domain | Why it is wrong / right |
| --- | --- | --- |
| $\sin(x)$ on $[-1,1)$ | native | little practical use — an arbitrary arc |
| $\sin(x)$ on $[-\pi,\pi]$ | one period | $\pi$ is not a power of two, so the endpoints do not land on a fixed-point grid |
| $\sin(\pi x)$ on $[-1,1)$ | one period | endpoints now on the grid; the $\pi$ was absorbed into $f$ |
| $\sin\!\big(\tfrac{\pi}{2}x\big)$ on $[0,1)$ | one quarter period | symmetries reconstruct the other three quarters ([[5.1) CORDIC]], Chap. 20) |

The last row is what a generator should actually be handed. The scaling costs nothing in hardware — it lives entirely in the constant that the table-filling code evaluates.

## Discretization issues

Mapping a continuous $f:[0,1)\to\mathbb{R}$ onto a finite grid in *and* a finite grid out creates two failure modes that are invisible in the real-valued mathematics. The first is catastrophic and the second is merely annoying, but both are corner cases that survive random testing.

### Range issues and their solutions

Let $\mathbb{F}_{\text{in}}$ be the $2^{n}$ points of the input format and $u = 2^{\ell_{\text{out}}}$ the output ulp. The output format $\mathrm{ufix}(m_{\text{out}},\ell_{\text{out}})$ represents exactly

$$\Big[\,0,\; 2^{\,m_{\text{out}}+1}-u\,\Big]\cap u\mathbb{Z}.$$

Correctness of the *format choice* is the condition

$$\max_{X\in\mathbb{F}_{\text{in}}}\;\mathrm{RN}\big(f(X)\big)\;\le\;2^{\,m_{\text{out}}+1}-u,$$

and the extrema in that condition are over the **discrete image**, not over the continuous range. The distinction is exactly what bites. Take $f=\sin(\tfrac{\pi}{2}x)$ on $[0,1)$ with $\ell_X=\ell_{\text{out}}=-4$, both formats $\mathrm{ufix}(-1,-4)$ (Fig. 16.5, p. 482). The continuous supremum of $f$ on $[0,1)$ is $1$, never attained — so "the range fits in $[0,1)$" looks true. But after rounding, $X=\tfrac{14}{16}$ and $X=\tfrac{15}{16}$ both give $\mathrm{RN}(f(X))=\tfrac{16}{16}=1$, which is **not representable**.

> [!warning] The failure is not an overflow, it is a wrap
> $\tfrac{16}{16}$ encodes as the 5-bit integer $10000_2$; truncated to 4 bits by the modulo property of fixed-point arithmetic it becomes $0000_2 = 0$. **The largest value of the domain is silently replaced by the smallest.**
>
> How many inputs are affected? The bad set is $\{X : f(X)\ge 1-u/2\}$, i.e. $X\ge\tfrac{2}{\pi}\arcsin(1-2^{\ell-1})$. Expanding $\arcsin(1-\varepsilon)\approx\tfrac\pi2-\sqrt{2\varepsilon}$ and counting grid points gives roughly $\tfrac{2}{\pi}2^{-\ell/2}$ of them out of $2^{-\ell}$ — a fraction $\tfrac{2}{\pi}2^{\ell/2}$ that **shrinks as the precision grows**: $2/16$ at $\ell=-4$, $10/256$ at $\ell=-8$, $162/65536$ at $\ell=-16$. The bug gets rarer and therefore harder to hit, and it lives at the very top of the domain, where neither random testing nor real input data usually goes. This is the one discretization bug worth being paranoid about; everything else on this page costs accuracy, not correctness.

Four fixes (Fig. 16.6, p. 483), none of them free:

| Fix | Mechanism | Cost |
| --- | --- | --- |
| **(a) Widen the output** | use $\mathrm{ufix}(0,\ell_{\text{out}})$, one extra MSB | exact, but ~half the output range unused; 8-bit in / 9-bit out |
| **(b) Saturate** | clamp $1$ to the largest representable value | possible hardware overhead; error at the two rightmost points rises from $\tfrac12$ ulp ($1/32$) to nearly $1$ ulp ($1/16$) |
| **(c) Round down** | define $\widetilde f = \mathrm{RD}(f)$ instead of $\mathrm{RN}(f)$ | error budget doubles to $1$ ulp everywhere |
| **(d) Scale $f$** | tabulate $(1-2^{\ell})f$ instead of $f$ | still *perfectly* rounded, but with respect to a modified function; total bound $\approx 1.5$ ulp against the original $f$ |

Fix (d) is the generic one and costs nothing in hardware, since the scale factor is baked into the generation-time constant. In FloPoCo, for 8-bit in and out:

```text
flopoco FixFunctionByTable f="255/256*sin(pi/2*x)" signedIn=false lsbIn=-8 lsbOut=-8
```

The factor is $1-2^{\ell}$ in general, writable in Sollya as `(1b8-1)/1b8` where `b` means "times two to the power". The resulting VHDL maps `00000000` to `00000000` and `11111111` to `11111111` (p. 490). Fix (d) has a variant — scale or shift the *input* instead — that does not apply to sine but often does elsewhere.

A second, sneakier version of the same problem (Fig. 16.7, p. 484): the reciprocal. Reduce $1/x$ to $[1,2)$ using $\tfrac{1}{2^{n}x} = 2^{-n}\tfrac{1}{x}$, then move to the standard domain as $\tfrac{1}{x+1}$ on $[0,1)$, then offset so the output also matches a format:

$$f(x)=\frac{2}{x+1}-1,\qquad f(0)=1,\quad f(1)=0.$$

Both the $+1$ and the $-1$ are trivial bit operations, so they cost nothing. But $f(0)=1$ *exactly*, so the output format needs the bit of weight $2^{0}$ for one single input value. In the intended use — $1/x$ wrapped in a leading-zero counter and a shifter, see [[2.6) Shifters]] — the reconstruction logic absorbs that extra bit, so it is tolerable. The command is `f="2/(x+1)-1" signedIn=false lsbIn=-8 lsbOut=-16`, which also shows that the output precision can far exceed the input precision.

### The monotonicity issue

**The positive result.** $\mathrm{RN}$, $\mathrm{RU}$ and $\mathrm{RD}$ are all non-decreasing maps $\mathbb{R}\to\mathbb{F}$. A composition of non-decreasing maps is non-decreasing, so if $f$ is monotonic then $\circ\!\circ f$ is monotonic for any of these $\circ$. **A correctly rounded implementation of a monotonic function is monotonic, for free.**

**The negative result.** Faithful rounding is *not a function* — it is a relation. A faithful operator may return either neighbour, chosen independently at each input:

$$\widetilde f(X)\in\Big\{\,u\big\lfloor f(X)/u\big\rfloor,\; u\big\lceil f(X)/u\big\rceil\,\Big\}$$

There is no single monotone $\circ$ to compose with, so the argument above collapses. Concretely: pick $X_1<X_2$ with $f(X_1)<f(X_2)$ but both strictly inside the same ulp interval $(ju,(j+1)u)$. The operator may legitimately return $(j+1)u$ at $X_1$ and $ju$ at $X_2$ — the output *decreases* while $f$ increases.

**How bad can it get?** Bound the drop, using monotonicity of $\lfloor\cdot\rfloor$ and $\lceil\cdot\rceil$ and $f(X_1)\le f(X_2)$:

$$
\widetilde f(X_1)-\widetilde f(X_2)\;\le\; u\big\lceil f(X_1)/u\big\rceil - u\big\lfloor f(X_2)/u\big\rfloor
\;\le\; u\big\lceil f(X_2)/u\big\rceil - u\big\lfloor f(X_2)/u\big\rfloor\;\le\; u
$$

so **a non-monotonicity of a faithful operator is never larger than one ulp** (p. 485). In the 4-bit sine of the plot above (widened to $\mathrm{ufix}(0,-4)$ by fix (a), so that $\tfrac{16}{16}$ is representable), $16f$ takes the values $15.311$, $15.693$, $15.923$ at $X=\tfrac{13}{16},\tfrac{14}{16},\tfrac{15}{16}$ — all three strictly inside $(15,16)$, so a faithful table could return $16,15,16$ and visibly wobble.

> [!note] When to pay for monotonicity
> Few applications care, and the only published study of the issue is Iordache and Matula, reviewed in [[4.2) Table-Based Function Evaluation]] (Sect. 17.2.10, p. 521). But when a downstream block does a binary search, a comparison against a threshold, or an inverse lookup, a one-ulp wobble breaks an invariant rather than degrading a number — and then several of the later architectures pay real area to guarantee monotonicity.

## Some classes of numerical functions

`sqrt` and `cos` look identical from the outside: same C prototype, comparable library performance, both irrational on trivial inputs ($\sqrt2$, $\cos\tfrac12$). They belong to different classes, and the class determines which techniques apply.

### Algebraic functions

An **algebraic function** is the solution of a polynomial equation in several variables $P(S,X,Y,\dots)=0$:

| Function | Defining polynomial |
| --- | --- |
| quotient $Q=X/Y$ | $P(Q,X,Y)=QY-X$ |
| square root $S=\sqrt X$ | $P(S,X)=S^2-X$ (positive root) |
| 2-D norm $N=\sqrt{X^2+Y^2}$ | $P(N,X,Y)=N^2-X^2-Y^2$ (positive root) |
| $S=X/\sqrt{X^2+Y^2}$ | $P(S,X,Y)=S^2(X^2+Y^2)-X$ |

$+,-,\times,/$ are themselves bivariate algebraic functions. Two consequences follow directly from "$P$ is built only from additions and multiplications":

**1. A digit-recurrence algorithm falls out of the definition.** Since $P$ is a combination of additions and multiplications, one can usually derive an evaluation algorithm using nothing else — that is exactly [[2.5) Dividers#SRT Division]] for the quotient, and its extensions to square root and to arbitrary rational functions via the E-method in [[4.4) Digit Recurrence for Algebraic Functions]].

**2. Faithful $\Rightarrow$ correctly rounded, cheaply.** On finite binary inputs, $P$ evaluates *exactly* and finitely. Even when $P(S,X,Y,\dots)=0$ is unachievable in finite binary, the residual value of $P$ is a finite, computable measure of the error — for Euclidean division, the residual $QY-X$ is literally the remainder. So (Fig. 16.9, p. 487): compute $S$ faithful to precision $\ell-1$, which is cheaper than aiming directly for correct rounding at precision $\ell$. Then

- if the LSB of $S$ is $0$, then $S$ is already a precision-$\ell$ number, and since $|\,\widehat S-S\,|<2^{\ell-1}$ it is necessarily the correctly rounded result at precision $\ell$;
- otherwise $S$ is a midpoint between two precision-$\ell$ numbers, and as long as $P$ is monotonic in $S$, the **sign** of $P(S,X,\dots)$ tells you whether $S>\widehat S$, $S<\widehat S$ or $S=\widehat S$ — and that sign is computable exactly with finite resources.

**Takeaway: for algebraic functions, any faithful technique converts into a correctly rounded one.** No such shortcut exists for the next class.

### Elementary and special functions

**Elementary functions** are the exponential and logarithm, the trigonometric functions (relatives of the exponential in the complex domain) and their inverses, plus any finite composition of these with algebraic functions. **Special functions** are, less formally, the useful mathematical functions that are *not* elementary — typically defined by an integral or an infinite series, e.g. `erf` and the Bessel functions in the C standard library. They are in general harder, and research is still active.

A useful intermediate class: a **D-finite** (or *holonomic*) function is the solution of a finite system of linear ODEs with polynomial coefficients. That class contains all algebraic functions, many (not all) elementary functions, and many useful special functions, and many properties and algorithms can be derived automatically from such a definition.

The one respect in which elementary and special functions are *fundamentally* harder is **correct rounding**. Ziv's generic algorithm computes it by successively increasing the working accuracy, and it fails hardware on two counts:

1. **Termination.** If the exact $f(X)$ is a midpoint, the loop never exits. Such inputs must be filtered out, which is sometimes easy ($e^{x}$ of a nonzero rational $x$ is irrational, hence never a midpoint) and sometimes hard.
2. **It is a `while` loop.** Data-dependent iteration counts make sense in software and much less sense in hardware.

Hence the book's scope, and this note's: correct rounding of elementary functions only for precisions up to about 24 bits, where the whole table of correctly rounded values can be enumerated offline in multiple precision. Which is precisely what plain tabulation does.

## A first generic approximator: simple tabulation

Plain tabulation has the **lightest requirements of any technique here**: it needs $f$ to be *defined, with a finite value, on its domain*. Nothing else. Every later method — multipartite, polynomial, digit recurrence — needs some form of differentiability or bounded derivatives on the interval. Tabulation also has **zero architectural overhead for correct rounding**: the complexity lives entirely in the offline code that fills the table.

### Tabulating precomputed function values in a ROM

The architecture is a ROM holding the values. The entries are computed at *generation* time, in arbitrary precision, by arbitrarily complex algorithms — FloPoCo delegates this to Sollya, whose relevant feature is not its coverage of elementary functions (essentially everything MPFR implements) but that it evaluates expressions **with guaranteed accuracy**, even through cancellations.

Four generator invocations that between them cover the whole failure taxonomy above (pp. 489–490):

| Case | Command | What it demonstrates |
| --- | --- | --- |
| No range issue | `f="sin(pi/4*x)" signedIn=false lsbIn=-8 lsbOut=-8` | image of $[0,1)$ lies inside $[0,1)$; identical in/out formats |
| Output reaches 1 | `f="255/256*sin(pi/2*x)" signedIn=false lsbIn=-8 lsbOut=-8` | scaling fix (d); the naive version needs a 9th output bit for one value |
| $[0,1)\to(0,1]$ | `f="2/(x+1)-1" signedIn=false lsbIn=-8 lsbOut=-16` | extra MSB tolerated because reconstruction logic consumes it; output precision $\gg$ input precision |
| Integer, discontinuous | `f="x*1b6*x*1b6-23*floor(x*1b6*x*1b6/23)" signedIn=false lsbIn=-6 lsbOut=0` | $x^2 \bmod p$ for modular multiplication via $ab=\frac{(a+b)^2-(a-b)^2}{4}$; wildly discontinuous, and tabulation does not care |

### Actual cost of a ROM

A table with $n$ address bits and $m$ output bits holds

$$B \;=\; 2^{n}\cdot m \quad\text{bits.}$$

The derivation is one line and it is the whole story. The input format has $2^{n}$ distinct codes; the table must store one $m$-bit entry per code, because tabulation makes no assumption relating $f$ at neighbouring addresses. Therefore **adding one input bit doubles the table; adding one output bit adds only $2^{n}$ bits.** In the book's words, the generated VHDL "is exponential in the input size, but only linear in the output size" (p. 490).

> [!important] The exponential is the reason Part 4 exists
> $$B = 2^{n}\cdot m$$
> With $m=n$: $n=8$ gives 2 kbit; $n=12$ gives 48 kbit; $n=16$ gives 1 Mibit; $n=24$ gives **384 Mibit (48 MiB)**. Sixteen bits is already past what you would spend a block RAM budget on, and 24 bits is not a circuit. Every technique in [[4.2) Table-Based Function Evaluation]], [[4.3) Polynomial Approximation]] and [[4.4) Digit Recurrence for Algebraic Functions]] is a different way of buying back that exponent — by splitting the address (multipartite), by storing coefficients instead of values (polynomial), or by storing nothing at all and iterating (digit recurrence).

$2^{n}\times m$ is the *conceptual* size, not the *cost*. Cost depends entirely on the target.

**On ASIC**, a small table is best regarded as a Boolean function and handed to standard logic synthesis, which is very good at it. Gustafsson and Johansson measured the resulting area empirically and found it strikingly symmetric in $k$ (inputs) and $n$ (outputs):

$$A \;\propto\; 2^{\,0.65\min(k,n)}\times 2^{\,0.19|k-n|} \tag{16.1}$$

The symmetry has a cause: synthesis both minimizes each output's expression *and* maximizes sub-expression sharing across outputs, so a gate graph mapping $k$ inputs to $n$ outputs costs about the same as one mapping $n$ inputs to $k$ outputs. Note the exponent $0.65<1$: logic optimization genuinely beats the raw bit count, but it does not remove the exponential.

Hard **ROM generators** are the alternative: transistor-level layout gives a very low cost per bit, since stored $0$s and $1$s reduce to wiring to the power rails and essentially all the logic is address decoding. But they lose layout flexibility and, crucially, they do not benefit from logic optimization — and in the same study, ROM generators came out *larger* than standard-cell implementations of the tabulated functions.

## Mapping to FPGA primitives

Two primitives implement a ROM on FPGA, and the smaller one sets the unit of cost.

**LUTs.** An $\alpha$-input, 1-output LUT *is* a $2^{\alpha}\times1$ ROM. A $2^{\alpha}\times n$-bit ROM is therefore $n$ LUTs in parallel, all sharing the same address (Fig. 16.11b, p. 492: $w_X=\alpha=6$, $n=8$). The consequences are quantized:

- a $2^{\alpha}\times n$ ROM costs $n$ LUTs — and so does a $2^{\alpha-1}\times n$ ROM, only half used. **Shrinking the address below $\alpha$ buys nothing.**
- at $w_X=\alpha+1$, each output bit costs 2 LUTs plus one address-decoding multiplexer, which the fabric may or may not give you for free.
- in general, $$\text{LUTs}\;=\;2^{\max(k-\alpha,\,0)}\times n.$$

That formula is no more reliable than $2^{k}\times n$ was on ASIC, and for the same reason: FPGA synthesis inherited the ASIC logic-optimization technology. On a $\alpha=6$ device, the $2^{8}\times8$ table for $\sin(\tfrac{\pi}{2}x)$ on $[0,1)$ synthesizes into **25 LUTs, not the predicted $2^{2}\times8=32$** (p. 492).

**Block RAM.** The second primitive, usable as ROM with contents loaded at configuration time (see [[Block Memory]]). It has a very coarse, discrete set of shapes and the same inflexibility as a hard ASIC ROM, but it is the right answer for tables of a few tens of kilobits — which, by the exponential above, means roughly $n\le12$.

## Trade-offs

Plain ROM against the three families that follow. The $2^{n}\cdot m$ and LUT columns are computed from the formulas above with $m=n$ and $\alpha=6$.

| $n=m$ | $2^{n}\cdot m$ bits | Same, in bytes | LUTs, $2^{\max(n-6,0)}\!\times\!m$ | Verdict |
| --- | --- | --- | --- | --- |
| 8 | 2 048 | 256 B | 32 (25 measured, p. 492) | trivially fine — just tabulate |
| 12 | 49 152 | 6 KiB | 768 | one or two block RAMs; borderline on LUTs |
| 16 | 1 048 576 | 128 KiB | 16 384 | most of a mid-range FPGA for one function |
| 24 | 402 653 184 | 48 MiB | 6 291 456 | not a circuit |

| Technique | Cost vs. input width $n$ | Accuracy | Latency | Stops being viable when |
| --- | --- | --- | --- | --- |
| **Plain ROM** (this note) | $\Theta(2^{n}m)$ bits; ASIC area $\propto 2^{0.65\min(n,m)}2^{0.19\lvert n-m\rvert}$ (eq. 16.1, p. 491) | correct rounding for free, no architectural overhead | one ROM access, combinational | $n\gtrsim12$; hard wall by $n=16$ |
| **[[4.2) Table-Based Function Evaluation]]** | still exponential, but with a much smaller exponent — LDTC halves a table, piecewise-linear tabulated products cut it by about an order of magnitude (p. 497) | faithful; correct rounding needs extra work | tables plus one or two adder delays | around $n=16$–$20$, where even the reduced exponential wins |
| **[[4.3) Polynomial Approximation]]** | stores $d+1$ coefficient tables addressed by the high bits — cost grows with the *degree needed for the accuracy*, not with $2^{n}$ | faithful; degree is the accuracy knob | $d$ multiply–add stages (Horner), pipelinable | $f$ not smooth enough on the interval, or degree grows too fast |
| **[[4.4) Digit Recurrence for Algebraic Functions]]** | $\Theta(n)$ area, no table at all | faithful $\to$ correctly rounded via the residual-sign trick above | $\Theta(n)$ cycles — one digit per cycle | $f$ is not algebraic, or the latency budget is a single cycle |

**Pick plain tabulation** whenever $n\le\alpha$ (it is literally free: $m$ LUTs) and up to about $n=12$ if block RAM is idle — it is the only technique needing no smoothness at all, so it is also the *only* option for discontinuous or table-defined functions. **Pick a table-and-addition or polynomial method** from $n\approx12$ upward for smooth elementary functions, trading a couple of adder or multiplier delays for one to two orders of magnitude of memory. **Pick digit recurrence** when $f$ is algebraic and you can spend cycles: it is the only family whose area is linear in $n$, and the only one where correct rounding is nearly free at any precision.

## Worked example — 4-bit $\sin(\tfrac{\pi}{2}x)$, and the trap

Format: $X\in\mathrm{ufix}(-1,-4)$, so $X=i/16$, $i=0\dots15$; output the same format; $u=2^{-4}=\tfrac1{16}$; $\mathrm{RN}$. Table entry $= \mathrm{RN}\!\big(16\sin(\tfrac{\pi}{2}\cdot\tfrac{i}{16})\big)$ in units of $u$.

| $X$ | $16f(X)$ | naive $\mathrm{RN}$ | stored word | scaled $16\cdot\tfrac{15}{16}f(X)$ | stored word |
| --- | --- | --- | --- | --- | --- |
| `0000` | 0.000 | 0 | `0000` | 0.000 → 0 | `0000` |

**Errors.** In the naive column, 14 of 16 entries are correctly rounded at $\le\tfrac12$ ulp; the last two are off by $\lvert 0-15.693\rvert = 15.693$ ulp and $15.923$ ulp — nearly the full dynamic range, from a bug that touches $2/16$ entries here and $10/256$ at 8 bits.

In the scaled column every entry fits. The error against the *scaled* function is $\le\tfrac12$ ulp by construction; the scaling itself contributes
$$\big|f(X)-\tfrac{15}{16}f(X)\big| = \tfrac{1}{16}\,\sin\!\big(\tfrac{\pi}{2}X\big)\;\le\;\tfrac1{16} = 1\ \text{ulp},$$
so the **total error against the original $\sin(\tfrac{\pi}{2}x)$ is at most $1.5$ ulp** — matching the book's bound for fix (d).

**Cost.** $2^{4}\times4 = 64$ bits. On a $\alpha=6$ FPGA this is $2^{\max(4-6,0)}\times4 = 4$ LUTs, and the two unused address bits are pure waste — the same 4 LUTs would have held a 6-bit-input table.

**Monotonicity.** The scaled $\mathrm{RN}$ column is non-decreasing, as guaranteed by the composition argument. A *faithful* table need not be: with the output widened to $\mathrm{ufix}(0,-4)$, $16f$ takes $15.311$, $15.693$, $15.923$ at the three largest inputs, all strictly inside the ulp interval $(15,16)$, so returning $16,15,16$ is faithful and non-monotonic — a wobble of exactly one ulp, the proven maximum.
