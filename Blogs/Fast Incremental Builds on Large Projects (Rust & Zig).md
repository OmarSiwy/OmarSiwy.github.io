VerA is a Verilog-AMS compiler and ESPice a SPICE simulator that compiles 86 device models through it, both in Zig. ESPice's merge gate costs about 7,400 CPU-seconds, over an hour on a four-core runner. On my machine a no-op `zig build` of VerA answers in 0.19 s, and a no-op `zig build check` over 32 steps in 0.26 s. The distance between those numbers is a cache, and a cache is exactly as good as the inputs declared to it. This article is the rules I follow to keep a rebuild near the second mark in Zig and in Rust, where each build system's cache comes from, and the cases where each one rebuilds too much.

## A build is a table

Mokhov, Mitchell and Peyton Jones reduce every build system to two parts: a scheduler that orders the steps and a rebuilder that decides whether a step runs ("Build Systems à la Carte", 2018). A rebuilder is minimal if it runs each step at most once and only when something it transitively depends on changed. It has early cutoff if a step whose inputs changed but whose output did not stops the rebuild right there. Make's rebuilder is a dirty bit from mtimes, minimal only while nobody touches a file, and without cutoff. Shake stores verifying traces, hashes of each step's inputs, and has cutoff. Bazel stores the outputs too, keyed by hash, and so can share them across machines. Nix keys outputs by the hash of the inputs alone, which needs determinism and gives up cutoff.

The three systems here each sit in one of those cells, and every rule below is a consequence of its row:

| | Rebuilder | What the key hashes | Early cutoff |
|---|---|---|---|
| Cargo | dirty bit | source mtimes, plus profile, features, flags and dependency fingerprints | no |
| rustc incremental | verifying traces | one 128-bit fingerprint per query result | yes, per query |
| Zig `std.Build` | input-addressed outputs, as Nix | the contents of every declared input file | no |

## Zig: the step is the unit

### A hit, exactly

Each step opens a `Cache.Manifest`, hashes its own options, declares every input path and asks for a hit. The manifest's file name under `.zig-cache/h/` is a hash of the input paths and flags, not of their contents, so one manifest exists per distinct step configuration. Inside it, each file carries its size, inode, mtime and a 128-bit SipHash of its bytes. A file whose stat still matches is a hit without being read. A file whose stat changed is hashed again and still hits if the bytes agree. A file whose mtime is not older than the cache's own last write is never trusted from stat alone, because the filesystem clock may not have ticked. The step's digest is the hash of every file digest, with the Zig version string mixed in, and its outputs are written under `.zig-cache/o/<digest>/`. That is Nix's model at step granularity: the address is the inputs, switching back to a state you built last week is a hit, a toolchain bump starts cold, and nothing is ever deleted. A hit takes a shared lock on the manifest, so several `zig build` processes can use one cache at once.

It also means no early cutoff. A downstream step's inputs include the path `o/<digest>/device.zig`, so when a generator's inputs change its output moves, and everything below it misses even when the generated bytes are identical. Figure 1 shows where that cost lands and how I dodge it.

### A Run step is cached when it is allowed to be

A Run step hashes its argv, environment and working directory and declares an input for every file argument. In Zig 0.17 (`lib/compiler/Maker/Step/Run.zig`) a run counts as having side effects, and is never cached, when any of these hold: `has_side_effects` is set, the step takes the command line's passthrough arguments, its stdio is inherited, or it has no output argument and captures nothing. A run with an `addOutputFileArg`, a captured stream, or an exit-code or stdout check is cached on its inputs. Three habits follow.

Give every generator an output argument and every test runner an exit-code check. VerA's `testRun` adds `expectExitCode(0)` for this reason alone: a test runner with no check reran on every build.

Declare what the program reads at run time with `addFileInput`. VerA's cross-module test walks the whole tree, so its build step declares every file under `lib`, `src`, `tools`, `tests` and `specification` as an input. The no-op build reuses the result, and a new fixture still invalidates it.

When the inputs really are discovered while the program runs, set `has_side_effects = true` instead of leaving the check off. Both disable the cache. One of them also says why.

0.17 caches a second thing: the configuration, meaning the result of running `build.zig` itself. A build script that reads the tree declares it with `dependOnDirectoryContents`, `dependOnFileContents` or `dependOnFileMetadata`, or calls `b.graph.poisonCache()` and reconfigures every time. ESPice's model discovery declares the `models` directory. VerA's fixture glob poisons the cache, because the directory dependency aborted 0.17 on Windows. Either answer is fine. An undeclared read is not.

### Keys are contents, not paths

`addCopyFile` in a WriteFile step hashes the source path, so a second worktree of the same tree missed every cached copy. VerA writes those files by contents instead, and the key is now identical from any checkout. The same rule decides how worktrees share: each one symlinks its `.zig-cache` to the main checkout's, so a result computed in one is a hit in all.

### Decide what the compiler sees

A Compile step compiles its whole module graph as one unit. Modules organise imports; they do not produce separate objects, so a one-line edit anywhere in the graph recompiles the artifact. The lever is which artifacts exist. ESPice compiles each of its 86 device models into its own object and links those objects into the simulator, the C library and the host tests that need them, so a model edit recompiles one object. The device objects import an ABI module whose `core` is only `core/ids.zig`, not the full `core`, so an edit elsewhere in `core` recompiles no model. Their copy of the GPU library module carries no kernel artifacts, so a kernel, a GPU architecture or a lane option changes without invalidating a host model or waiting on `ptxas`. And each model gets its own WriteFile wrapper, because one shared step moves every wrapper's path when one model changes: the no-cutoff rule again, one level down.

In VerA the test devices are Zig files emitted by the compiler under test. A cached generator run depends on the compiler binary, so every compiler edit regenerated every device and rebuilt every object and host test built from it. `-Dva-cache`, on by default, copies the compiler to a fixed path under `zig-out/gen` and invokes it by that plain string, so the run's key covers its arguments, the model's source, every file it `include`s and `lib/contract.zig`, and not the compiler. That is early cutoff by hand, and it is a lie the build tells itself: after a codegen change the devices are stale until `-Dva-cache=false`. The flag is documented at the point of use because that is the only honest way to keep it.

### The edit loop

Full builds are for CI. The loop is `zig build check --watch -fincremental`. A `check` step compiles every root with `use_llvm = false` and emits no binary, so an edit is re-checked in under a second. Two facts from the 0.17 source shape that command: `-fincremental` is honoured only under `--watch` or the web UI, so it does nothing on a one-shot build, and the watcher waits a 50 ms debounce before rebuilding. Incremental state lives per artifact in `.zig-cache`, so one watch per artifact across all worktrees. The 0.17 notes call incremental compilation possible for most projects on x86_64 Linux and keep it off by default; the 0.16 notes list known bugs including miscompilations. So the watch build is for diagnostics, and the result that counts comes from a plain build. The payoff is real: the 0.14 notes measured the 500,000-line Zig compiler at 14 s for the first analysis and 63 ms per edit under `-fincremental --watch` with no binary emitted.

On x86_64 Linux a Debug build defaults to Zig's own backend rather than LLVM, about five times faster by the 0.15.1 notes, which is why `check` is cheap; macOS and Windows Debug builds still go through LLVM. It is also why ESPice's merge gate builds ReleaseSafe only: the two backends disagreed on numeric results and an allocation count, and a gate that runs on one backend proves nothing about the other.

### Two caches, and nothing collects them

Zig keeps a local cache per project and a global one (`ZIG_GLOBAL_CACHE_DIR`, `~/.cache/zig` by default) for fetched packages and the compiled build system itself, the maker, built once per Zig version. Two builds of the same Zig version from different Nix store paths share that one entry and evict each other, after which every `zig build`, even `--help`, recompiles it for about two minutes. Both projects' dev shells name the global cache after the toolchain's store path, and the symptom is gone.

Nothing deletes either cache. VerA's `.zig-cache` is 64 GB: 24 GB of step outputs in 915 digests, 1,294 manifests, and 33 GB the test suite itself parks there. ESPice's is 167 GB, with 14 GB more in `zig-out` and, since 0.16 unpacks every package into the project's own `zig-pkg/`, six old versions of VerA sitting there. A `zig gc` with default caps of 1, 2 and 4 GiB for the global, local and package caches is specified in proposal #30193 and not implemented, and #36858 would collect during `--watch`; until one ships, collection is a person's job: a byte budget per cache, old `o/` entries deleted only while no build runs, and never a routine `rm -rf .zig-cache`, which throws away the warm state the budget exists to protect.

### CI

A hosted runner starts cold. `mlugg/setup-zig` points both Zig caches at one `.zig-cache` directory and saves it per job under GitHub's 10 GB per-repository cap, but wipes it before saving once it passes 2 GiB. VerA's cache list shows what that means at this size: the gate's entries are 0 MiB, wiped every run, while the small jobs save 70 to 250 MiB each, and 100 entries hold 4.9 GiB of the 10 GB cap. Raise `cache-size-limit` or accept a cold gate; either way the budget goes to shape. `zig build build-all -Dtarget=<t>` compiles every artifact for five targets and runs none, because a foreign binary cannot run on the runner. The release job cross-compiles all five in a loop on one runner rather than a five-job matrix that would repeat the release check five times. RAM-bound jobs pass `-j2 --summary failures`, and `--maxrss` is not a substitute: it schedules steps within one build from their declared estimates and caps nothing machine-wide. One shell line bit me: `zig build test 2>&1 | tail` swallows the exit code and produced a green report over a failing build. Gate on `${PIPESTATUS[0]}`.

## Rust: the crate is the unit

### What Cargo knows

Cargo's unit is the crate. For each unit it stores a fingerprint under `target/<profile>/.fingerprint`: a hash over the rustc version, profile, enabled features, target, `RUSTFLAGS`, the `[lints]` table, the compile mode and the fingerprints of the immediate dependencies, plus the list of source files from rustc's dep-info. The unit is dirty if that hash changed, if any source file's mtime is newer than the dep-info, or if any output is older than a dependency's output. Nothing compares outputs, so there is no early cutoff: an edit to a private function in a dependency rebuilds every dependent. Registry and git dependencies have no mtime tracking at all; only path crates do. Consequences that cost real minutes:

- `RUSTFLAGS` is in the fingerprint and in the artifact file names. Changing it rebuilds the whole graph. Set flags once in `.cargo/config.toml`, never in a shell for one command.
- `cargo check` and `cargo build` are different compile modes whose artifacts are not shared (cargo#3501, still open). Alternate between them and you keep two graphs warm.
- Under the default feature unification, `cargo check -p a` and a workspace-wide `cargo build` can resolve different features for the same dependency, which is a different fingerprint, and `cargo test` adds dev-dependency features under resolver 2. The workspace-wide mode is still nightly (`-Zfeature-unification`); a `cargo-hakari` workspace-hack crate is the stable fix.
- rust-analyzer's `cargo check` in the same target directory takes the lock the terminal build needs. Set `rust-analyzer.cargo.targetDir` and the two never meet.
- mtimes are the dirty bit, so a fresh checkout is all new and a touched file is a rebuild. Content hashes (`-Zchecksum-freshness`) are still unstable, with a call for testing in September 2026.
- Since Cargo 1.99, incremental compilation defaults to off when the `CI` variable is set. It never applied to registry dependencies, only to workspace members and path dependencies.
- `build.build-dir`, stable since 1.91, separates intermediates from final artifacts; the layout-v2 work on nightly adds finer locking and cleanup of stale units. This is where Cargo's own fixes are landing.

### What rustc remembers

rustc's incremental mode is the Shake cell. Every query result carries a 128-bit fingerprint in a dependency graph persisted under `target/<profile>/incremental`. On the next build a query is marked green without running when all of its inputs are green, red when an input's result hash changed, and a red query that recomputes to its old hash turns green and its dependents stop there. That is real early cutoff at query granularity, and at the back end it reuses object files per codegen unit. It is on in `dev` and `test`, off in `release`, and it raises codegen units from 16 to 256 so reuse is finer. Its cost is the fingerprinting itself, which the compiler's own guide names as the main reason an incremental build can be slower than a clean one.

### The levers, with their numbers

In the order I apply them:

1. **Linker.** LLD is the default on x86_64 Linux since Rust 1.90. On ripgrep it cut link time 7x and an incremental rebuild 40% end to end. Elsewhere, opt in with `-C link-arg=-fuse-ld=mold` (or `linker = "clang"` plus the path); mold links Clang 21 in 1.3 s where LLD takes 6.2 s, and wild is faster than LLD and not yet incremental.
2. **Debuginfo.** `[profile.dev] debug = "line-tables-only"` and `[profile.dev.package."*"] debug = false`. The Rust Performance Book puts `debug = false` at 20 to 40% of a dev build; the 2025 compiler survey measured line tables alone at 2 to 30% of cycles. Keep a `debugging` profile that inherits `dev` with full debuginfo for the day a debugger is needed.
3. **Optimised dependencies.** `[profile.dev.package."*"] opt-level = 3` makes a simulator's tests tolerable, with one trap: generic sharing is off at opt-level 2 and 3, so optimised dependencies export no monomorphisations and your own crates instantiate every generic again.
4. **`cargo build --timings`.** The report draws the unit graph and its critical path. Proc-macro crates cannot be pipelined and block every dependent, so `syn` and its users sit on that path; `cargo llvm-lines` shows which generics the leaf crate pays for.
5. **Crate split.** Dependents rebuild whenever a dependency rebuilds, so the only way to shrink a rebuild is to shrink the crate the edit lands in and keep it off the trunk of the graph: thin, hot leaves; stable interfaces inward.
6. **Tests.** `cargo nextest` builds the same binaries, then runs each test in its own process in parallel where `cargo test` runs the binaries serially; its archive moves built binaries to other CI machines and `hash:m/n` partitions them deterministically.

Still nightly in October 2026: the parallel front end (`-Zthreads=8`, up to 50% in the 2023 announcement; its stabilisation plan was accepted in July 2026 with six to nine months of steps), the Cranelift back end (20% wall and 40% CPU on its own debug build), and checksum freshness. Plan for them; do not depend on them.

### Caches and collection

sccache caches a crate only when rustc emits a linked `rlib` without calling the system linker, so `bin`, `cdylib`, `dylib` and `proc-macro` crates are never cached, and it needs incremental compilation off. That makes it a CI tool for dependencies and nothing else. `Swatinem/rust-cache` keys on the lockfile and toolchain, strips incremental state and non-dependency artifacts before saving, and shares the same 10 GB cap. Cargo 1.88 added collection of the global cache, registry files unused for three months and generated files for one. Target directories have none (cargo#13136), and four of mine sum to 92 GB, so `cargo clean -p` and `cargo-sweep` stay in the routine.

## The checklist

For a new `build.zig` or `Cargo.toml`, before the first slow build:

1. Every step that produces something has an output argument, and every step that only checks has an exit-code or stdout check.
2. Every file a step reads at run time is declared, or the step says `has_side_effects`.
3. Keys hash contents, never absolute paths.
4. The artifact graph is cut where edits land: one object per generated unit, narrow imports for the shared ones, kernel and codegen artifacts out of host graphs.
5. One shared generator, cached on its inputs; any input deliberately left out is named in the option that leaves it out.
6. The edit loop is a check step under `--watch`; the gate is a plain build.
7. One global cache per toolchain, a byte budget per cache, and collection that runs only while no build does.
8. Flags live in config files, and `cargo check`, `cargo build`, `cargo test` and the editor agree on features, profile and target directory.
